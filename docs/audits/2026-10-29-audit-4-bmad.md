# Audit 4: Kahnban vs the BMAD Method

**Date:** 2026-10-29
**Kahnban:** `C:\github\kahnban`, engine 1.4.0 (README.md:3), `main` @ a38a0c0
**BMAD reference:** BMAD-METHOD branch **`V6.12`** (the current stable line, "frozen except for bug fixes"; V7 is in preview alpha on `main`, per the repo landing page https://github.com/bmad-code-org/BMAD-METHOD). The docs site https://docs.bmad-method.org is already written against the V6.12 skill set. TEA (Test Architect) is a separate module, documented at https://bmad-code-org.github.io/bmad-method-test-architecture-enterprise/.
Source files cited as `V6.12:<path>` resolve under `https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/V6.12/<path>`.

> **Important framing.** The BMAD most people remember is v4/early v6: a Scrum Master writes stories with Dev Notes, a QA persona writes gate files, PRD and architecture are sharded, and planning uses "Quick Flow / BMad Method / Enterprise" tracks. **V6.12 has moved on from most of that.** Its agent roster has no Scrum Master and no QA persona (docs `reference/skills-and-agents`). `bmad-create-story` and `bmad-dev-story` survive only as deprecation shims (`V6.12:src/bmm-skills/v6-shims/README.md:7-21`, "Removal rides the v7 cut"). Sharding now appears only as a glob fallback (`V6.12:src/bmm-skills/v6-shims/bmad-create-story/SKILL.md:89-92`). The named tracks were replaced by size-of-intent paths (`V6.12:docs/plan/choose-a-planning-path.md:94-107`). This audit compares Kahnban against **current** BMAD and treats the classic features as legacy. BMAD itself retired several of them, which is evidence for the DON'T-STEAL list.

## 1. Reference summary (BMAD V6.12)

**Roles** (docs `reference/skills-and-agents`): Analyst (Mary), PM (John), Product Owner (Sofia: "turns requirements into tickets, slices epics, manages the board, replans"), Architect (Winston), Developer (Amelia: "builds code, generates QA tests, reviews code, runs epic retrospectives") and UX Designer (Sally). The Technical Writer (Paige) is on hiatus. There is no Scrum Master and no QA persona. QA is split three ways: Dev, the review skills, and the optional TEA module.

**Phases and paths.** Analysis, planning and solutioning are *tools, not stages*: "These are independent tools, not stages. Pick the ones the gap calls for" (`choose-a-planning-path.md:50-52`). They all converge on one skill, **`bmad-spec`**, which condenses any well-defined intent into `SPEC.md` and, on request, an ordered `stories.yaml` (`:31-37`, `:83`). Path size follows intent: trivial (no BMad), one session (`bmad-build`), epic-sized (spec, then Story Breakdown, then one Build per story, then retrospective), and project-sized (PRD, UX and architecture only as needed, then `bmad-spec` per epic) (`:94-163`). "Every path uses the same implementation unit" (`:105-107`). Input ceiling: "roughly a 40-page document ... condense them first" (`:25-29`).

**Artifacts.**
- Brief, PRFAQ, PRD (`prd.md` + `addendum.md` + `.memlog.md`), UX (`DESIGN.md`, `EXPERIENCE.md`) and `ARCHITECTURE-SPINE.md` (`:74-86`).
- `SPEC.md` + `stories.yaml`. Stories carry only `id/title/description/spec_checkpoint/done_checkpoint/invoke_dev_with`, and there is explicitly "No `status` field, ever" (`V6.12:src/bmm-skills/plan/bmad-spec/assets/stories-schema.md:5-23`).
- Per-story spec files (`stories/<id>-<slug>.md`) that carry status in frontmatter.
- `sprint-status.yaml`, only for the PRD/epics path (`break-work-into-stories-and-track-it.md:195-203`).

**Story context engineering** (the core idea, now in `bmad-build-auto`):
1. **Epic context compiled once and cached.** `epic-<N>-context.md` holds a distilled 800–1500-token digest of PRD, architecture and UX for that epic, with sections Goal / Stories / Requirements / Technical Decisions / UX / Cross-Story Dependencies. Its rules: "Describe by purpose, not by source", "Nothing derivable from the codebase", and it is invalidated when any planning file is newer (`V6.12:.../bmad-build-auto/compile-epic-context.md`, whole file; validity check in `step-01-clarify-and-route.md:55-61`).
2. **Previous-story continuity.** Each story loads the prior done story's **Code Map, Design Notes, Spec Change Log and task list** (`step-01:63`; the folder+id variant loads *every* sibling story, `step-01:34,37`).
3. **Per-story spec, written by the planner.** `<intent-contract>` holds Intent, Boundaries (Always/Never) and the I/O and edge-case matrix, and it is read-only to the implementer. Below it come a **Code Map** of annotated paths, Tasks & Acceptance in Given/When/Then, an append-only **Spec Change Log** and **Review Triage Log**, Design Notes and Verification commands, all in a 900–1600-token budget (`V6.12:.../bmad-build-auto/spec-template.md`).
4. **The spec is the sole handoff.** "Do not add parent-authored goal restatements ... the spec is the subagent's sole source of truth" (`step-03-implement.md:137`).

**Story lifecycle:** `draft → ready-for-dev → in-progress → in-review → built/done`, plus `blocked` and `dropped`. Resume is status-driven (`step-01:20-25`). Build Auto "never moves a ticket to `done`" (docs `build/autonomous-development-loops`). In V6.12 source, step-04 writes `status: done` on its own spec file (`step-04-review.md:268-275`), so the docs and the code disagree slightly.

**Gates / QA model:**
- **READY FOR DEVELOPMENT standard.** The spec must be Actionable, Logical, Testable (Given/When/Then), Surface-anchored, Complete, Sufficient and Coherent. It gets one repair attempt, then the run halts (`workflow.md:86-96`, `step-02-plan.md:101-107`).
- **Intent gap:** "Multiple defensible readings ... do not resolve one by picking a reading. HALT" (`step-02:98`).
- **Verify:** the orchestrator reads the diff itself, "Judge against the diff, not against the implementation subagent's report" (`step-03:149`). The **Matrix Test Audit** requires every edge-case row to have a test that ran and passed, and a test that disagrees with the matrix must never be edited to match the code (`step-03:153-155`).
- **Review:** parallel review layers (edge-case hunter, verification-gap, and others) are followed by an orchestrator **triage**. It renders verdicts high/medium/low/false/maybe-false, then routes each finding to **intent_gap** (revert, save the patch, halt for the human), **bad_spec** (revert, amend the spec, re-implement), **patch** (fix in place) or **defer** (record in frontmatter). The repair loop is capped at 5 iterations (`step-04-review.md:188-254`).
- **Verification-gap reviewer:** asks "if the behavior broke where it's actually used, would verification fail?" (`review-prompts/verification-gap.md`).
- **Readiness gate before sprint tracking:** PASS/CONCERNS/FAIL on "could a developer implement these epics without inventing decisions nothing records?" (`bmad-sprint-planning/references/readiness-gate.md:7-20`).
- **Epic retrospective:** an Accepted / Accepted-with-open-items / Rejected verdict against the epic's acceptance criteria, where any unfinished story forces Rejected (`bmad-retrospective/references/acceptance-verdict.md:51-73`).
- **TEA trace gate:** PASS/CONCERNS/FAIL computed from P0/P1/overall requirement-coverage thresholds (P0 100%, P1 ≥90%, overall ≥80%), written to `trace/gate-decision-{scope}.json` (TEA `how-to/workflows/run-trace`).

**Scale-adaptive behaviour:** size-of-intent paths plus `spec_checkpoint`/`done_checkpoint` per story, so a human reviews foundational stories before automating repetitions: "Give those decisions human attention before automating repetitions of them" (`choose-a-planning-path.md:129-137`).

**Modules:** BMad Method, Builder, Creative Intelligence Suite, Test Architect, **BMad Loop** (the unattended epic orchestrator, which "does not yet dispatch from the ticket tree" per docs `autonomous-development-loops`) and Game Dev Studio.

## 4. Verdict narrative

### SUCCEEDS: Kahnban beats BMAD here
- **Gates are code, not prose.** BMAD's READY standard, verification and triage are LLM instructions inside a skill. The workflow's own HALT protocol is markdown the agent must follow (`workflow.md:36-78`). Kahnban's gates are Python functions that refuse transitions: a frozen contract hash (`core.py:457-472`), diff containment to the blast radius, red proof (`docs/how-it-works.md:105`), reviewer ≠ owner, and a merge queue that retests the merged result (`how-it-works.md:211-230`). A lying agent cannot pass them.
- **Independent review.** BMAD reviews inside the same run that wrote the code (`step-04-review.md:166`, "review subagents must run at the same model capability"). Kahnban's reviewer is a different worker that holds no edit rights (`roles.json:48-67`), and the runner enforces the outcome.
- **Shipped orchestrator.** `kahnban run` already does what BMad Loop only describes, including parallel workers, leases, max_attempts escalation, attended/unattended autonomy and a guard hook (README.md:186-227). Live runs exercised refine → done, a rejection loop, and a merge-queue refusal (IMPLEMENTATION_STATUS.md:32-43).
- **Status cannot drift.** Folders are status, and every move is a commit. BMAD needs a repair mode for `sprint-status.yaml`.
- **Learnings → structural fixes** (four-level ladder, `README.md:245-255`) is more rigorous than BMAD's retro action items, which the retro only *proposes* (`acceptance-verdict.md:36-39`).
- **Intake interrogates only as needed.** `/grill-with-docs` asks in rounds, looks facts up itself and stops when nothing is assumed (`grill-with-docs/SKILL.md:12-15`). This matches the north star better than BMAD's brief/PRFAQ/PRD stack.

### MEETS
- Spec-as-contract with R-ids and coverage (BMAD has no requirement IDs that tickets must cite).
- Per-ticket AC → named test → auto-tick (README.md:127-135) is functionally BMAD's Given/When/Then plus Matrix Test Audit, and stricter (it is run, not judged).
- Escalate-instead-of-guess (`roles.json` `escalate_when`) is BMAD's `intent gap` HALT.

### FALLS SHORT
1. **Context handoff into each ticket is thin.** The coder prompt is the role steps plus blast radius plus test commands plus rejection notes (`handoff.py:237-260`). It is not told to read the spec, the ADRs or `design_docs`. The spec-analyst reads them (`roles.json:15`) but writes nothing of them down: `## Implementation notes` stays empty, because the analyst's steps cover only AC, Blast radius and Validation (`roles.json:16-18`). BMAD's best idea is that the planner's investigation is **drained into the story file** as a Code Map so the implementer never re-explores (`step-02-plan.md:95-96`). Kahnban discards it.
2. **No cross-ticket continuity.** Ticket N+1 from the same spec knows nothing about what N learned or built. BMAD loads sibling stories' Code Map, Design Notes and Change Log (`step-01:34,63`).
3. **No spec-level (epic) digest.** Each analyst re-reads the whole spec, ADRs and code for every ticket. BMAD compiles once and caches with mtime invalidation (`compile-epic-context.md`).
4. **Single-lens review with no triage taxonomy.** The reviewer checks hollow tests and scope (`roles.json:62`). It has no verification-gap lens ("would a break where it's used be caught?"), no edge-case hunt, and no routing of findings into patch, spec defect or intent gap. Every rejection goes back to the coder, even when the root cause is a bad ticket. That is BMAD's `bad_spec` case (`step-04:217,231`).
5. **No per-ticket human checkpoints.** `human_gates` is board-wide (README.md:221). BMAD lets you flag only the foundational stories (`stories-schema.md:12-13`).
6. **Slicing is not a factory step.** `/to-tickets` is an interactive skill. `kahnban run` only refines tickets that already exist (`dispatcher.py:200-218`).

### FAILS
1. **No "spec done" verdict.** `spec coverage` is complete when every R-id is *cited* by some ticket, whatever its column (`specs.py:183-210`). Nothing checks that all of a spec's tickets reached `5-done`, or that the combined result meets the R-ids once integrated. BMAD's retrospective rejects an epic with any unfinished story (`acceptance-verdict.md:61-73`) and judges the combined result against the spec. Kahnban's merge queue tests each merge, but nobody asks "is R3 actually delivered end to end?"
2. **No automated decomposition of a large document.** `ingest` on an arbitrary PRD is a heading-splitter (`ingest.py:314-445`, "Ingestion is heuristic", `adapters/PLAN-INGESTION.md:51-55`). On a spec it reads only `## Tickets`, which a human-driven `/to-tickets` must write first. "Hand it a 40-page spec and walk away" therefore stops at step one.

### Where BMAD is heavier than a solo dev + agents needs
- **Persona theatre** (named agents, menus, party mode, `bmad-advanced-elicitation`). BMAD itself dropped the SM and QA personas. Kahnban's role manifest (`roles.json`) is the right weight.
- **Document stack** (brief → PRFAQ → PRD → UX → architecture → epics → readiness → sprint status). BMAD's own docs say "You need a PRD when more than one person must agree" (`choose-a-planning-path.md:62-65`). A solo dev doesn't.
- **Sharding.** It is a token workaround for giant docs and is now a legacy glob fallback. The epic digest replaces it.
- **`sprint-status.yaml` with repair/validate modes.** It exists because YAML status drifts. Folders-as-status already makes it impossible.
- **Markdown HALT protocols, `customize.toml` overrides and step-file snapshots.** This is ceremony to make prompts behave like code. Kahnban already has code.
- **TEA's full module** (ATDD, NFR assessment, framework setup, teach-me-testing). Kahnban's red-proof plus per-criterion tests cover the core. Only the coverage-threshold idea is worth borrowing.

## 5. North-star gap

| North-star capability | Today | Blocker |
|---|---|---|
| Idea → interrogate only as needed | `/grill-with-docs` (good) | Interactive by design. Correct: this *is* the human gate |
| Spec → breakdown (tickets, tests) | Human runs `/to-tickets`, then `ingest --ready` | No factory role turns an approved spec into `## Tickets`; spec-analyst works on one ticket at a time |
| Epic → story hierarchy | SPEC ⊃ tickets via `spec:`/`covers:` | No spec status, no spec-scoped dispatch ordering, no spec close-out |
| Context into each story | Ticket + Log + QA contract | No digest, no Code Map, no sibling continuity, coder not pointed at the spec |
| Autonomous dev loop | **Strong**: `kahnban run`, gates, escalation, parallel jobs | Rejection loop cannot tell a "bad ticket" from "bad code" |
| Whole spec → done, walk away | Partial | (a) no auto-decomposition; (b) no "spec delivered" gate; (c) no >40-page condensation step; (d) no foundational-ticket checkpoint, so you must choose all-attended or all-unattended |

**The minimal path to "hand it a spec and walk away":**
1. The human approves the spec (keep this as the single human gate, README.md:163).
2. A **planner** factory role writes `## Tickets` from the approved spec plus a compiled spec digest, then ingests.
3. The runner executes the tickets with a digest and sibling context in each prompt.
4. A **spec close-out** gate gives an acceptance verdict once all `covers:` tickets are done.

Steps 2 and 4 are the only missing pieces. Everything else exists.

### DON'T-STEAL
- **Named personas, agent menus, party mode, advanced elicitation.** Theatre. Roles are already data in `roles.json`, which is the right abstraction.
- **Brief / PRFAQ / separate PRD / UX docs / readiness ceremony for solo work.** BMAD itself says a PRD is for multi-person agreement (`choose-a-planning-path.md:62-65`).
- **Document sharding.** A legacy token hack, superseded by the digest (#1).
